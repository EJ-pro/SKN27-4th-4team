# 요구사항 분석

## 기능적 요구사항

### 운동 백과

- 사용자는 전체 운동 목록을 조회할 수 있어야 합니다.
- 사용자는 운동명으로 검색할 수 있어야 합니다.
- 사용자는 카테고리, 장비, 난이도 기준으로 운동을 필터링할 수 있어야 합니다.
- 운동 목록은 페이지 단위로 나뉘어 표시되어야 합니다.
- 사용자는 운동 카드를 선택해 상세 정보를 볼 수 있어야 합니다.
- 운동 상세 화면은 설명, 대상 근육, 권장 시간, 예상 칼로리, 장소, 홈트 가능 여부, 척추 부하, 가이드, 시작 자세, 주의사항을 제공해야 합니다.
- 관련 운동이 있는 경우 관련 운동을 선택해 해당 운동 상세로 이동할 수 있어야 합니다.

### 주간 루틴

- 사용자는 통증 부위, 분할 방식, 운동 요일, 운동 목표, 운동 시간을 입력할 수 있어야 합니다.
- 시스템은 입력 조건을 기반으로 요일별 운동 루틴을 생성해야 합니다.
- 루틴은 운동명, 세트, 반복, 장비, 설명, 대체 운동을 포함해야 합니다.
- 사용자는 대체 운동으로 루틴 항목을 교체할 수 있어야 합니다.
- 사용자는 운동 완료 상태를 체크할 수 있어야 합니다.
- 루틴은 device UUID와 주차 기준으로 저장/조회되어야 합니다.

### AI 운동 상담

- 사용자는 상담 세션을 생성할 수 있어야 합니다.
- 사용자는 기존 상담 세션 목록을 볼 수 있어야 합니다.
- 사용자는 세션 이름을 변경하거나 삭제할 수 있어야 합니다.
- 사용자는 운동 관련 질문을 입력할 수 있어야 합니다.
- 시스템은 챗봇 답변을 생성하고 사용자 메시지와 봇 메시지를 저장해야 합니다.
- 챗봇은 운동 데이터와 대화 이력을 참고해 답변해야 합니다.
- 운동 범위를 벗어난 질문은 거절 메시지를 반환해야 합니다.

### 게스트 사용자

- 로그인 없이도 device UUID 기반으로 상담과 루틴을 저장할 수 있어야 합니다.
- 추후 로그인 구현 시 user 테이블과 device 기반 데이터를 연결할 수 있어야 합니다.

## 비기능적 요구사항

### 성능

- 홈 화면은 전체 운동 상세 데이터를 불러오지 않아야 합니다.
- 운동 목록은 상세 필드를 제외한 경량 데이터로 렌더링해야 합니다.
- 상세 정보는 사용자가 운동을 선택했을 때만 추가 요청해야 합니다.
- 목록 카드에서는 GIF/MP4를 기본 로드하지 않아야 합니다.
- 루틴 페이지처럼 상세 가이드가 필요한 화면만 full API를 사용합니다.

### 확장성

- 운동 데이터 필드가 추가되어도 목록 API와 상세 API를 분리해 영향 범위를 줄여야 합니다.
- 챗봇 RAG 노드는 질문 유형 분류, 검색, 답변 생성을 분리해 확장 가능해야 합니다.
- 주간 루틴은 scheduler와 daily routine을 분리해 요일별 저장과 수정이 가능해야 합니다.

### 유지보수성

- 프론트엔드는 페이지 단위 lazy loading을 사용합니다.
- 백엔드는 View 단위로 API 책임을 나눕니다.
- Docker Compose로 DB, backend, frontend 실행 환경을 분리합니다.
- 배포 전에는 `.dockerignore`, 정적 미디어 분리, ML 의존성 분리 같은 이미지 최적화가 필요합니다.

### 신뢰성

- DB 초기화 시 schema, muscle schema, exercise loader, vector DB loader가 순서대로 실행되어야 합니다.
- 루틴 저장은 transaction으로 처리되어 중간 실패 시 데이터 일관성을 보장해야 합니다.
- 챗봇 메시지는 사용자 메시지 저장 후 답변 스트림/생성 결과를 저장해야 합니다.

### 사용성

- 운동 목록은 필터, 검색, 페이지네이션을 제공해야 합니다.
- 챗봇 답변은 질문 아래에 표시되어 사용자가 질문과 답변을 함께 볼 수 있어야 합니다.
- 운동 상세는 좌우 이동과 관련 운동 이동을 지원해야 합니다.

## AB 테스트 결과

정식 사용자 그룹을 나눈 AB 테스트는 아직 수행하지 않았습니다. 현재 기록된 결과는 코드 개선 전/후를 비교한 성능 A/B 테스트입니다.

### 운동 목록 API 성능 비교

| 항목 | A안: 기존 전체 응답 | B안: 목록/상세 분리 |
|---|---:|---:|
| `/api/exercises/` 응답 크기 | 2.53 MB | 0.24 MB |
| `/api/exercises/` 응답 시간 | 약 2.3초 | 약 0.63초 |
| 홈 추천 API | 없음 | `/api/exercises/featured/?limit=8`, 2.2 KB, 약 0.37초 |
| 상세 API | 없음 | `/api/exercises/1001/`, 3.4 KB, 약 0.36초 |

### 결과 해석

- 목록 API 응답 크기는 약 90% 감소했습니다.
- 목록 API 응답 시간은 약 70% 이상 감소했습니다.
- 홈 화면은 전체 운동 데이터 대신 추천 8개만 요청하도록 변경되어 초기 부하가 크게 줄었습니다.
- 목록 카드의 GIF/MP4 기본 요청을 제거해 운동 목록 진입 시 미디어 요청 수를 0개로 만들었습니다.

### 채택안

- 운동 목록과 상세 데이터를 분리한 B안을 채택합니다.
- 루틴 페이지처럼 전체 가이드가 필요한 화면은 `/api/exercises/?full=1`을 사용합니다.
- 운동 목록과 홈 추천 섹션은 경량 API와 정적 썸네일을 사용합니다.
