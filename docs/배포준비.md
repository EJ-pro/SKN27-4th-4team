# 배포 준비 점검

현재 프로젝트는 로컬 개발 환경 기준으로 잘 돌아가지만, 그대로 운영 배포하면 깨질 수 있는 지점이 있다. 아래 항목은 배포 전에 우선 확인해야 할 하드코딩/운영 이슈 목록이다.

## 1. 운영 서버 실행 방식

### 백엔드가 Django 개발 서버로 실행됨

- 위치: `docker-compose.yml`
- 현재: `python manage.py runserver 0.0.0.0:8000`
- 문제: `runserver`는 개발용 서버라 운영 트래픽 처리, 안정성, 보안 면에서 부적합하다.
- 권장: `gunicorn config.wsgi:application --bind 0.0.0.0:8000` 같은 WSGI 서버로 변경한다.

### 프론트엔드가 Vite 개발 서버로 실행됨

- 위치: `frontend/Dockerfile`
- 현재: `CMD ["npm", "run", "dev"]`
- 문제: Vite dev server는 운영 정적 서빙용이 아니다.
- 권장: `npm run build` 결과물인 `dist/`를 Nginx, Caddy, S3/CloudFront 등으로 서빙한다.

## 2. API 주소 하드코딩

### `localhost:8000` API 주소

- 위치:
  - `docker-compose.yml`
  - `frontend/src/pages/ExercisePage.jsx`
  - `frontend/src/pages/RoutinePage.jsx`
  - `frontend/src/pages/ConsultPage.jsx`
  - `frontend/src/components/ExerciseSection.jsx`
- 현재: `VITE_API_URL=http://localhost:8000` 또는 fallback `http://localhost:8000`
- 문제: 배포 후 사용자의 브라우저에서 `localhost`는 배포 서버가 아니라 사용자 PC를 가리킨다.
- 권장:
  - 같은 도메인 배포라면 `/api` 상대 경로로 통일한다.
  - 프론트/백엔드 도메인이 다르면 `VITE_API_URL=https://api.example.com`처럼 운영 API 도메인을 주입한다.
  - 운영 빌드에서는 fallback localhost를 제거하거나 명확한 에러를 내게 한다.

## 3. Django 운영 설정

### `DEBUG=True`

- 위치:
  - `backend/config/settings.py`
  - `.env`
  - `.env.sample`
- 현재: 기본값과 샘플이 `DEBUG=True`
- 문제: 운영에서 디버그 페이지와 내부 정보가 노출될 수 있다.
- 권장: 운영 `.env`는 반드시 `DEBUG=False`.

### `ALLOWED_HOSTS`가 localhost만 허용

- 위치:
  - `backend/config/settings.py`
  - `.env`
  - `.env.sample`
- 현재: `localhost,127.0.0.1`
- 문제: 실제 도메인/IP로 접근하면 Django `DisallowedHost` 오류가 날 수 있다.
- 권장: 운영 도메인과 서버 IP를 명시한다.

예:

```env
ALLOWED_HOSTS=example.com,www.example.com,api.example.com
```

### CORS가 localhost만 허용

- 위치: `backend/config/settings.py`
- 현재:

```python
CORS_ALLOWED_ORIGINS = [
    'http://localhost:5173',
    'http://127.0.0.1:5173',
]
```

- 문제: 운영 프론트 도메인에서 API 호출 시 CORS 오류가 발생한다.
- 권장: 환경변수 기반으로 운영 도메인을 주입한다.

예:

```env
CORS_ALLOWED_ORIGINS=https://example.com,https://www.example.com
```

## 4. SPA 라우팅 배포 이슈

- 위치: `frontend/src/App.jsx`
- 현재: `BrowserRouter` 사용, `/exercise`, `/routine`, `/consult`, `/login` 경로 존재
- 문제: 운영 정적 서버에서 `/exercise`로 직접 접속하면 서버가 실제 파일을 찾으려다 404를 낼 수 있다.
- 권장: 정적 서버에 SPA fallback 설정을 추가한다.

Nginx 예:

```nginx
location / {
    try_files $uri $uri/ /index.html;
}
```

## 5. GIF/영상 정적 파일 서빙

### Vite dev server 미들웨어 의존

- 위치: `frontend/vite.config.js`
- 현재: `/gifs`, `/videos`를 Vite dev server middleware에서 파일 시스템으로 직접 서빙
- 문제: 운영 빌드(`dist/`)에서는 이 미들웨어가 동작하지 않는다. 따라서 운동 GIF/영상 경로가 깨질 수 있다.
- 권장:
  - `public/gifs`, `public/videos` 아래로 정적 파일을 배치한다.
  - 또는 Nginx에서 `/gifs`, `/videos` 경로를 실제 파일 디렉터리로 alias 처리한다.
  - 또는 별도 object storage/CDN에 올리고 URL을 데이터/API에서 제공한다.

Nginx alias 예:

```nginx
location /gifs/ {
    alias /srv/app/media/gifs/;
    expires 7d;
}

location /videos/ {
    alias /srv/app/media/videos/;
    expires 7d;
}
```

### 영상 베이스 경로 확인 필요

- 위치: `frontend/vite.config.js`
- 현재: `VIDEO_BASE = path.resolve('?대룞_3D?곸긽')`
- 문제: 깨진 문자열/로컬 경로로 보이며, Docker/Linux 운영 환경에 해당 디렉터리가 없으면 `/videos/...`가 전부 404가 된다.
- 권장: 실제 배포 경로를 명확히 정하고 환경변수 또는 정적 서버 설정으로 분리한다.

## 6. DB 노출

- 위치: `docker-compose.yml`
- 현재: `5432:5432`
- 문제: 운영에서 DB 포트를 외부에 공개하면 보안 위험이 커진다.
- 권장: DB는 Docker 내부 네트워크에서만 접근하게 하고 외부 포트 매핑을 제거한다.

## 7. 외부 리소스 하드코딩

- 위치:
  - `frontend/index.html`
  - `frontend/src/components/Hero.jsx`
  - `frontend/src/components/AlgorithmSection.jsx`
  - `frontend/src/components/ChatSection.jsx`
  - `frontend/src/components/ExerciseSection.jsx`
- 현재: Google Fonts, Unsplash 이미지 URL 하드코딩
- 문제:
  - 외부 네트워크/CSP 정책에 따라 이미지나 폰트가 로드되지 않을 수 있다.
  - 운영 서비스라면 라이선스/속도/캐싱 정책을 확인해야 한다.
- 권장: 핵심 이미지는 프로젝트 asset 또는 CDN으로 관리한다.

## 8. 환경변수 샘플 정리

- 위치: `.env.sample`
- 현재:
  - `SECRET_KEY=django-insecure-change-me-in-production`
  - `DEBUG=True`
  - `DB_PASSWORD=yourpassword`
  - `ALLOWED_HOSTS=localhost,127.0.0.1`
- 문제: 운영 설정 예시로 쓰기에는 위험하다.
- 권장:
  - `.env.sample`은 개발용임을 명시한다.
  - 운영용 예시는 `.env.production.sample`로 분리한다.
  - `SECRET_KEY`, `DB_PASSWORD`, `OPENAI_API_KEY`는 실제 값 커밋 금지.

## 9. 권장 배포 구조

### 단일 도메인 구성

```text
https://example.com/          -> frontend dist
https://example.com/api/...   -> backend reverse proxy
https://example.com/gifs/...  -> static media
https://example.com/videos/... -> static media
```

장점:

- 프론트 API 주소를 `/api`로 단순화 가능
- CORS 문제 최소화
- 쿠키/세션 확장 시 유리

### Compose 분리 권장

- `docker-compose.yml`: 개발용
- `docker-compose.prod.yml`: 운영용

운영 Compose에는 다음을 반영한다.

- backend command: `gunicorn`
- frontend: Nginx 정적 서버
- DB 포트 외부 노출 제거
- 운영 `.env` 사용
- `DEBUG=False`
- 운영 `ALLOWED_HOSTS`, `CORS_ALLOWED_ORIGINS`
